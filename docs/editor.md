# 物理示意编辑器 v0.2

> v0.3 更新：[动画工作区与独立工程](animation-and-projects.md)。顶部改为菜单和工作区；工程保存包含场景、草稿和历史。下文保留基础文档/组件机制，场景 JSON 是交换格式。


原生 C++ / Vulkan 桌面程序。可用鼠标编排运动示意，也可通过 MCP 操作同一个正在运行的场景。原有立方体与运动学 demo 仍是独立目标。

## 启动

在项目根目录执行：

```powershell
.\run-editor.ps1
```

`run-editor.ps1` 先调用共用构建入口 `build-editor.ps1` 做增量编译，成功后才启动固定的 `build/vs2022/bin/editor/Release/physics_editor.exe`。构建以 cmake 退出码为准：失败立即停止，提示先保存并关闭已打开的编辑器窗口，不会退回旧的可执行文件，也不会自动结束进程；脚本没有跳过编译的开关。脚本会等待编辑器退出并把它的退出码返回给调用者，因此编辑器运行期间该终端保持占用。Debug 与 Release 是同一份源码的两个配置：

```powershell
.\run-editor.ps1 -DebugBuild                          # build/vs2022/bin/editor/Debug/physics_editor.exe
.\run-editor.ps1 -Project .\path\to\example.physproj  # 可选：启动时打开工程
```

`build-editor.ps1` 只做两件事：`cmake --preset vs2022` 配置，然后 `cmake --build --preset release|debug --target physics_editor` 增量构建。需要单独配置编辑器时仍可加 `-DBUILD_01_CUBE=OFF -DBUILD_02_KINEMATICS=OFF`；`build/verify-runtime` 是历史验证用过的临时构建目录，不是常用入口。VS Code 的 **Physics editor (Debug)** 配置通过 preLaunchTask 调用同一入口（`.vscode/tasks.json`），通用 CMake 目标配置不变；Visual Studio 仍将 `physics_editor` 设为启动项目。

## 编辑流程

1. 从右侧“添加图元…”菜单添加质点、线段、箭头、圆、圆弧、矩形、折线、地面、文字或公式。
2. 点击画布图形或对象列表进行选择。拖动图形会暂停动画并修改初始位置，一次拖动是一条可撤销命令。锁定对象仍可在属性面板编辑。
3. 右侧输入数值或文字后按 Enter 提交。`x/y` 是初始位置；线段和箭头的 `dx/dy` 是相对端点。折线顶点可在“完整属性 JSON”中修改。
4. 给图元添加 `vx/vy/ax/ay` 匀加速运动，或绑定到另一个独立对象。速度箭头使用目标的瞬时速度；其他绑定表示位置跟随。不能同时拥有自己的运动和绑定，也不允许绑定链。
5. 使用播放、时间轴和“解题步骤”预览。对象的“出现步骤”决定何时显示，步骤从 0 编号。“步骤数”减少到已有对象步骤以下时会拒绝，应先修改对象。
6. 使用文件菜单保存或打开 `.physproj` 工程；`.json` 路径仅用于当前文档导入/导出。文档导入、删除、修改都可撤销/重做；工程打开先验证再切换，不属于文档内撤销；关闭有未保存修改的窗口会提示。运行时的播放进度不写入场景文件，重新打开从当前合法进度预览，可点击“|<”。

中键平移、滚轮整体缩放（含文字、公式）、“适应画布”居中显示当前内容。Ctrl+Z / Ctrl+Y 撤销重做，Ctrl+S 保存整个工程。完整 JSON 编辑区保存未识别的扩展字段，核心结构错误会拒绝提交。颜色控件的一次连续调整合并为一条历史（控件松开或选择切换时提交/取消）；拖动画布也只产生一条。滚轮缩放超过 `referenceZoom` 时是位图字形/公式遮罩的放大，画面会变软，这是固有代价（R3）。

## 单位与物理含义

场景坐标使用米，时间使用秒，正 x 向右、正 y 向上。速度是 m/s，加速度是 m/s²。每个独立运动对象按解析式计算：

\[
\mathbf r(t)=\mathbf r_0+\mathbf v_0t+\tfrac12\mathbf at^2,
\qquad \mathbf v(t)=\mathbf v_0+\mathbf at.
\]

速度箭头长度使用单独的比例，不与位移共用量纲；地面只是示意图元，不会自动产生碰撞。默认上抛场景将时长设为返回地面的时间；改变初始条件后需要同步调整时长、文字和公式。这一版不自动证明文字与运动参数一致，也不解析自然语言题目、不自动求解或执行通用物理仿真。

公式可选内置资源，也可直接输入受限数学 LaTeX，在后台编译成工程资产；无需修改源码或重新编译。文字、公式随画布整体缩放。受限 LaTeX 不加载 CJK 宏包，公式图元只能排版数学；中文与公式混排请拆成“文字图元 + 公式图元”（R5）。操作和依赖见 [公式与导出](runtime-formulas-and-export.md)。

## Write 手写入场

文字与公式对象可以附加可选的 `write` 字段：播放时按 Manim `Write` 的思路出现——先沿字形轮廓逐步描绘，再填充。不引入 Manim 运行时，文档版本仍是 1，没有 `write` 的旧工程渲染完全不变。

- 右侧属性面板“Write 手写入场”负责添加、修改和移除；人类界面与 MCP 走同一条命令路径（`apply_commands` 里的 `set_write`，`write: null` 表示移除），因此共用一条可撤销事务和同一份操作记录，工程存档与撤销/重做都覆盖它。
- 参数：`start` 与 `duration`（秒）必填，且 `start + duration` 必须落在场景时长内；`stagger`（默认 0.35）是相邻单元起笔的错开量，0 表示同时；`phase`（默认 0.65，允许范围 0.05–0.95）是每个单元内描边所占的时间比例，其余时间用于填充——`phase` 必须小于 1，以便给填充阶段保留时间；`outline` / `fill` 可以只留一个阶段（不能同时关闭）；`outlineWidth`（默认 1.5，屏幕像素）与 `easing`（`linear` / `smooth`）。未知字段、越界数值、类型不符都会被拒绝，批量命令保持原子性。
- 单元划分：文字按字符，空格和换行也占节拍。内置公式和新生成的运行时公式使用**书写计划**（`writingPlan`）：同一字形的多块墨迹合成一个节拍（例如 `=` 的两条线），外层先从左到右，分式按“分数线→分子→分母”递归展开，主体后跟上下标；根号与内部内容连续，常见求和/积分符号先于上下限，向量箭头和帽子跟在主体后。公式示例和界面新添的公式入场采用 `stagger=1`，一个单元完成后再写下一个；已有工程的显式设置不变。
- 顺序来自 PDF 对象和排版几何的规则推断，并非完整 TeX 语法解析。已验证普通及嵌套分式、两行 aligned、常见上下标和根号；极端间距或复杂跨行装饰不保证符合书写习惯，整式上横线可能先于内容出现。旧自定义公式缺少计划、计划推导失败或不匹配掩码时沿用空间阅读序；可重新生成 LaTeX 公式获得计划。字形归属按 PDF 对象标识关联，保存数据另有尺寸、数量和覆盖校验。
- 求值：给定对象与时间点即可算出每个单元的描边/填充进度，不读取任何历史帧。播放、暂停、任意前后跳转与离屏导出因此看到同一画面；`t <= start` 什么都不画（0 进度不显字），`t >= start + duration` 交回普通绘制路径，完成帧与未设置 `write` 时逐像素一致。
- 轮廓几何：文字在固定 64 px 的 CPU 光栅上用 marching squares（覆盖阈值 128、沿像素中心线性插值）提取亚像素闭合轮廓；公式复用现有 RLE 遮罩做同样处理。几何在文本或公式资源变化时构建并缓存（最近 24 项 LRU），不会每帧扫描掩码，也不随视图缩放重建。
- 描边落在真实字形上：文字的行进位置与字距完全按**当前字体图集的真实度量**排布（与 `ImFont::RenderText` 同一套取整规则），再把这个字形在当前图集里的真实包围盒作为目标矩形，把 64 px 高分辨率轮廓按 x/y 独立缩放映射上去。因此交互画布（基准 18 px × 密度）与导出进程（按导出光栅密度）各自的字形都与描边重合，不依赖某个固定字号。
- 填充保留原始覆盖：文字直接绘制当前字形的 UV 四边形（与整串 `AddText` 同一条顶点算术，所以临近结束帧与结束帧之间不跳变）；公式按每个连通区域拥有的 texel 跨度绘制**原遮罩纹理的子矩形**，低覆盖率的抗锯齿边缘保留真实 alpha，并包含一圈透明的双线性过滤支持邻域；跨度互不重叠（每个 texel 至多画一次），孔洞天然排除。没有二值化颜色填充，也没有整屏擦除。
- 描边就是真实轮廓：每个闭合轮廓单独绘制，断开的墨迹之间不会连出多余的线；笔尖带一个圆点，描边透明度随该单元填充进度淡出，收尾不会在字形外留下光晕。
- **中文说明**：轮廓来自字形覆盖掩码，不是字体矢量路径，因此也**不是汉字真实笔顺**。一个汉字会拆成若干墨迹连通区域，按“上到下、左到右”的光栅顺序描绘；这能给出自然的书写感，但不代表书写顺序。真实笔顺需要带书写顺序的笔画或中心线路径数据；普通字体矢量轮廓本身也不包含笔顺，属于后续工作。
- 组件定义内部仍是静态图元：`write` 与 `motion`/`binding`/`animation` 一样不能放在定义子图元上，请把入场动画加在主场景对象上；校验会明确拒绝。把场景时长改短到某个 `write` 窗口装不下时，`settings` 会像已有动画分段一样被拒绝，需要先改窗口。

### 复现 demo 与导出帧

```powershell
# 启动后：示例 → 手写入场（中文 + 公式），或
# 文件 → 导入当前文档 JSON，路径填 scenes/write-entry.json
```

该场景时长 6 s，四个对象分别在 0.0 / 0.8 / 1.8 / 3.2 s 起笔（中文标题 `size` 56、中文说明 `size` 36、两个公式 `scale` 2.0），纵向排布紧凑，便于直接导出 1280×720 观察。导出用已有的“文件 → 导出动画…”：格式选 `PNG 帧目录` 会逐帧写 `frame_%06d.png`（24 fps、6 s → 144 帧），也可以直接选 MP4/GIF；MCP 侧等价请求：

```json
{"method":"export_animation","args":{"output":"exports/write-entry.mp4","format":"mp4","view_mode":"fit","width":1280,"height":720,"fps":24}}
```

导出的每一帧都由同一个纯时间函数求值（帧 i 取 `i/fps`），所以按帧号抽查就能看到“轮廓推进 → 填充”的过程，而不依赖播放顺序。`scenes/write-entry.json` 由 `build/vs2022/apps/editor/<配置>/physics_write_entry_test.exe --emit-demo scenes/write-entry.json` 生成，`editor_write_entry` 测试会比对代码生成结果与仓库文件，防止两者漂移。

## MCP

初始化独立 Python 环境：

```powershell
.\mcp\setup.ps1
```

推荐用脚本启动 MCP（先增量编译，再以 stdio 传输运行服务）：

```powershell
.\run-editor-mcp.ps1              # 先增量编译，再启动 MCP 服务
.\run-editor-mcp.ps1 -DebugBuild
```

它固定调用 `build/mcp-venv/Scripts/python.exe mcp/server.py --workspace <仓库根> --editor-transport stdio --start-editor <刚构建的 exe>`。stdio 传输会启动自己的可见编辑器窗口，不连接已有命名管道；MCP 的 stdout 只承载协议，构建进度和诊断全部写 stderr，脚本也不重定向、不缓冲、不吞掉 Python 的标准输入输出。缺少 `build/mcp-venv` 时会明确提示先运行 `.\mcp\setup.ps1`。注册到宿主时请带上 `-NoProfile -ExecutionPolicy Bypass -File`：配置文件或交互式输出写进 stdout 会破坏协议流。宿主在服务启动前会等待本轮配置与增量构建（首次配置通常数秒到数十秒），超时上限很小的宿主应先把构建跑热。

注册到本机 Codex（需已经编译 Release；也可以把 `run-editor-mcp.ps1` 注册成服务命令，让宿主每次先增量构建）：

```powershell
.\mcp\setup.ps1 -RegisterCodex
```

服务名 `physics-editor`，使用官方 MCP Python SDK 1.30.0 的 stdio 传输。服务可自动启动编辑器；宿主结束 MCP 进程时可能一并回收自动启动的窗口，因此退出或重载服务前应先保存场景。`setup.ps1 -RegisterCodex` 注册的是连接命名管道的默认传输，需要独立控制窗口的生命周期；`run-editor-mcp.ps1` 使用的 stdio 传输总是启动自己的编辑器窗口，两者不要同时用来操作同一个场景。Codex 重新加载 MCP 配置后才会发现新增工具；接入方式见 [官方文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)。

提供 26 个工具，基础 12 个为：`get_catalog`、`get_scene`、`apply_commands`、`replace_scene`、`undo`、`redo`、`set_playback`、`save_scene`、`load_scene`、`show_editor`、`get_view_state`、`get_history`。新增 6 个组件与历史回溯工具见 [接口说明](components-and-history.md#mcp-合同)。文档工具接受 scope=scene/component，默认 scene；不根据当前标签页猜测范围。先发现能力和读取场景；修改时提交最近读取的 `expected_revision`。不同客户端同改场景时，旧修订被拒绝，不会默默覆盖。调用超时后先查询状态，不能直接重发修改。

### MCP 操作时显示原生窗口

默认勾选“跟随 MCP 显示”。MCP 修改场景或时间轴时，编辑器会显示窗口、从最小化状态恢复，并使用与人类操作相同的画布渲染。没有另建一份无界面的场景。Windows 可能限制应用抢占键盘焦点，因此恢复显示不承诺始终抢占前台输入。

`show_editor` 可显式请求显示窗口。`get_view_state` 返回可见/最小化状态、已呈现帧数、最近已呈现画布的 `presentedRevision` 和 `presentedTime`；这能区分“命令已接受”和“新状态已提交呈现”，不表示显示器完成物理扫描。画布几何按**物理帧缓冲像素**报告：`canvasWidth/canvasHeight`、`zoom`、`referenceZoom`、`origin`、`pan` 都乘过 `framebufferScale`，并附带该比例；`origin` 是画布内部原点到世界原点的像素偏移。取消“跟随 MCP 显示”后可以自行最小化窗口，后台请求仍正常响应。

### 人和 MCP 的统一操作历史

![独立历史面板的实际渲染截图](editor-component-history.png)

点击顶部“操作历史”查看当前文档的会话记录。滑块和成功修改记录可进入历史只读预览，恢复此状态会生成新的可撤销操作；历史时间轴与物理秒数时间轴分开。创建、修改、删除、移动、排序、场景设置共用相同的编辑命令；保存/打开、撤销/重做以及主动播放/定位请求也有日志。每条记录包含序号、UTC 时间、来源、原始命令参数、前后修订、播放状态、执行结果；失败请求附带原因，撤销/重做关联原操作序号。

人类可直接撤销 MCP 的修改，MCP 也可撤销人类的修改。批量命令按一次事务记录和撤销；画布拖动在松开鼠标时提交一条 move。鼠标位置变化、查询、自动播放的每一帧不写入日志。颜色及时间轴滑块仍按每次实际提交记录，尚未合并整个滑动手势。

日志自动写入启动目录的 `history/session-*.jsonl`，通常位于项目根目录，首行保存会话初始场景，后续逐行保存操作；加载文件时还保存解析后的文档，避免日志只依赖一个可能变化的文件名。每条记录刷新到文件，文件不会随应用正常退出删除。磁盘写入失败会给出明确提示，内存操作仍可继续，应保存场景并检查日志状态。

界面和 `get_history(after, limit)` 分页查询完整审计，单页最多 100 条。工程保存完整审计及有界撤销快照，重开后可继续撤销；独立 JSONL 仍用于会话恢复检查。很大的请求在界面/API 摘要中省略参数，完整参数保存在工程和磁盘日志中。编辑历史状态保留最近 101 个，撤销最多 100 步。

来源 `human` 表示界面入口，`mcp` 表示 MCP 入口，`system` 表示系统操作。MCP 也可能由人类客户端发起，所以这个字段不冒充真实身份认证。

例如，读取修订号后，用 `apply_commands` 添加一支箭头：

```json
{
  "expected_revision": 0,
  "commands": [{
    "op": "create", "id": "force-arrow", "type": "arrow", "name": "辅助箭头",
    "properties": {"x": 3, "y": 4, "dx": 2, "dy": 0}
  }]
}
```

多个相关命令放进同一个数组，只产生一条历史记录。可读回文档确认结果，再移动时间轴检查运动；MCP 不通过模拟鼠标来实现编辑。保存/打开限制在配置的工作区内；没有 shell 执行、任意代码或远程监听工具。本地管道只允许当前所有者访问并拒绝远程客户端。

可手动连接已有编辑器，隔离不同实例：

```powershell
.\build\vs2022\bin\editor\Release\physics_editor.exe --pipe lesson-a
.\build\mcp-venv\Scripts\python.exe mcp/server.py --pipe lesson-a
```

同一管道名只允许一个编辑器，避免误连。标准输出只用于 MCP；原生程序日志走服务的标准错误。

显式 `--stdio` 是编辑器侧的 JSON 行传输（stdin/stdout），协议占用标准输出、诊断重定向到标准错误；它经 Python MCP bridge 封装后对外就是标准 MCP 协议，native 侧只负责 JSON 行传输，因此不是“非完整 MCP”。MCP 服务端 stdio 接入已经 MCP 端到端验证通过（`editor_stdio`），不再待接入。新增 MCP 工具（如 `set_formula`/`export_animation`）对已连接客户端不会自动可见，客户端需要刷新/重连，服务端不保证推送（A5）。运行目录可用 `--data-dir` 显式指定；显式目录不可用时不会静默替换，只有自动模式才回退到可写目录并在 `[runtime]` 行报告，场景与资源目录分别解析。窗口启动位置按显示器工作区夹取，避免侧栏与播放条落到屏幕外（U1）；这不是完整的逐显示器 DPI 矩阵处理。

## 验证

```powershell
cmake --build --preset debug
ctest --preset debug --verbose
.\build\mcp-venv\Scripts\python.exe mcp/test_integration.py
```

核心测试覆盖批量原子性、修订冲突、撤销/重做、解析运动、引用完整性、无效值、中文路径往返和注册新图元/命令。UI smoke 注入真实 ImGui 鼠标事件，验证添加和拖动，再覆盖窗口缩放、最小化恢复和关闭。MCP 测试通过官方客户端连接真实原生编辑器，验证工具发现和实际编辑，不使用假的场景后端。

`editor_write_entry` 专门覆盖 Write 入场：亚像素轮廓（含软覆盖边缘的插值）、掩码非零偏移（轮廓、跨度与包围盒一起平移）、抗锯齿边缘归属（每个有覆盖的 texel 及一圈过滤支持邻域恰好属于一个区域，弱灰度笔画不丢失，区域不重叠）、断开的墨迹不连线、对角相邻像素不合并、孔洞不填充、单元顺序（文字按字符 / 公式按阅读序）、**书写计划**（计划顺序与分组生效、`=` 的双横线合成一个单元、尺寸/分量数/重复/缺失/越界任一不符即回退阅读序、计划仍恰好铺满每个 texel 且不丢墨迹、内置 `flight` 计划的前三个单元是 `T`、`=`、分数线且分数线排在分子分母之前）、`get_catalog` 契约（必须是对象，且 `write.appliesTo/default/note` 齐全）、时序边界（0 进度不显字、`phase=1` 被拒绝、`phase=0.95` 的填充只在窗口末完成、恰好完成、越界钳制、错开与缓动）、纯时间求值（正放/倒放/重复求值一致且单调）、文档契约（`set_write`、`create` 携带 `write`、非法对象与越界拒绝、撤销/重做、存盘往返、组件定义拒绝）以及真实中文字形链（同一字体光栅 → 轮廓 → 单元，并检查轮廓落在各自字符格内）和 demo 场景（字号/公式 scale、窗口不超出场景时长、与仓库文件逐字段一致）。

`tools/test_formula_writing_plan.py` 覆盖计划生成本身：合成原子验证分数线识别（上下都有墨迹）、分式先横线、嵌套递归（含内外跨度相同）、**aligned 上下两行独立分式不互认嵌套**、分母里再套分式、`\overline` 跟随所在分子侧、厚块不算分数线、**主体优先**（算子先于上下限、箭头/帽子跟在底数之后、宽箭头覆盖一行时先出该行字形）、分数线的局部连通带不被跨行墨迹撑开；假 page/text page 验证**按对象标识归属**（两个对象包围盒完全相同也不抢错字形）、过滤合成空白、没有对应对象即拒绝；合成掩码验证"包含 texel 的最小框优先"（大根号框不吞被开方字形）、粘连的根号+上横线仍是一个单元、无框墨迹直接拒绝；真实 PDF 集成测试走 `render_formula`（运行时同一条路径）验证 flight、简单分式、三种嵌套、aligned 两行、两种 `\overline`、`\sum`/`\int`/`\vec`/`\hat`、根号分式与分量覆盖；`BuiltinPlanTableTest` 直接核对生成的计划表与 `formula_cache.hpp` 里 28 个缓存掩码（尺寸、连通域数、每个分量恰好一次）。`editor_project` 覆盖旧工程（无计划）加载到有计划的新库、新工程加载到无计划的库，以及非法/错配计划被拒绝。

`editor_write_rendering` 通过独立可见窗口检查前后 seek，再将几乎完成的帧与普通绘制逐像素比较，最大颜色通道差不能超过 2/255；同时验证 PNG 导出与 Vulkan 校验。

`mcp/demo_client.py` 是可读的官方 SDK 客户端示例，会连接/启动编辑器、读取场景并定位时间。`scenes/vertical-throw.json` 是通过 MCP 保存的默认上抛场景，可直接在编辑器中打开。
