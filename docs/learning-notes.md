# 学习笔记：立方体中的 Vulkan 与三维概念

## 当前需求中的术语

“Vulkan + C++ 图形程序”的说法正确，`cpp` 是常见简写，正式名称是 C++。“使用 VS Code 或 Visual Studio 编译”日常表达也能理解；严格来说，VS Code 是编辑器，Visual Studio 是 IDE，MSVC 才是这里的编译器，CMake 负责生成构建配置，MSBuild 执行构建。

安装 Vulkan SDK 提供头文件、链接库、着色器编译器、验证层与诊断工具。程序运行还依赖显卡驱动实现的 Vulkan 能力。SDK 版本不等于设备支持版本，扩展和功能还需要查询并显式开启。

## 建议的阅读顺序

1. `math.hpp` 与 `shaders/cube.vert`：理解顶点如何经过模型、视图、投影变换。
2. `cubeVertices()`：一个立方体有 6 个面，每面 2 个三角形，此处使用 36 个顶点。
3. `createVertices()`、`createPipeline()`：顶点数据布局如何与着色器输入对应，深度测试如何开启。
4. `record()`：附件布局转换、清屏、绑定管线和顶点缓冲、传递矩阵、绘制、转换至呈现布局。
5. `drawFrame()`：取得交换链图像、等待同步、提交绘制和呈现。
6. `recreateSwapchain()` 与 `cleanup()`：窗口变化、资源依赖和销毁顺序。

## 三维变换和深度

这里使用列向量，矩阵按列主序存储，着色器计算：

```text
clipPosition = Projection * View * Model * localPosition
Model = RotationY * RotationX
View = TranslationZ(负距离)
```

矩阵从右向左作用于向量。模型变换把立方体从自身坐标放到世界坐标；视图变换相当于把相机放在 Z 正方向并朝 -Z 看；透视投影使远处的物体看起来更小。视口是竖屏时，相机自动后移以保持完整画面。

Vulkan 常用深度范围为 **0 到 1**，不要直接搬用默认 OpenGL 的 -1 到 1 投影公式。这里近裁剪面映射到 0，远裁剪面映射到 1。正高度视口使屏幕 Y 向下，因此投影矩阵翻转 Y。矩阵测试专门检查这些约定。

深度缓冲每帧清为 1；片元通过 `LESS` 比较后才写入颜色与深度。关闭深度测试会导致后绘制的面覆盖先绘制的面，无法保证遮挡正确。背面剔除用于排除背向相机的三角形，与深度测试的职责不同。

顶点颜色是线性值，优先使用 sRGB 交换链格式完成输出编码。画面的颜色差异用于区分面，目前不是光照计算结果。

## Vulkan 资源与同步

- Instance 表示应用与 Vulkan 的实例连接；Physical Device 是实际 GPU；Device 是程序创建的逻辑设备。
- Surface 连接系统窗口与 Vulkan；Swapchain 管理交替呈现到窗口的图像。
- Image 存储图像数据，Image View 描述以什么格式与范围使用图像，不能把二者当成同一对象。
- Pipeline 描述着色器及固定功能状态；Command Buffer 记录要交给 GPU 执行的工作。
- Fence 可供 CPU 等待；这里的二进制 Semaphore 用于队列操作之间的等待。

`vkQueueSubmit` 返回不代表 GPU 已经完成。提交 fence 完成也不等于窗口呈现操作已经释放资源。按交换链图像索引分配呈现等待信号量，可以避免错误重用；本例进一步使用 `VK_EXT_swapchain_maintenance1` 的呈现 fence，在调整窗口和退出时明确等待呈现资源释放。这不是等待像素实际扫描到显示器上的精确计时机制。[Khronos 同步说明](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html)

获得图像遇到 `OUT_OF_DATE` 时不能先重置提交 fence 再返回，否则下一帧可能永远等待一个不会被提交操作触发的 fence。获得 `SUBOPTIMAL` 图像仍会消耗 acquire 信号量，应该完成对应提交与呈现后再重建。

## 有意采用的简化与限制

- Windows 原生 Win32 窗口，避免初学阶段的第三方包管理。Vulkan 本身跨平台，但这份窗口代码目前不跨平台；有 Linux/macOS 需求时再引入窗口抽象，macOS 还涉及 Vulkan 实现选择。
- 使用 Vulkan 1.3 动态渲染，不创建传统 `VkRenderPass` / `VkFramebuffer`。现有机器支持该路径；这不是所有 Vulkan 设备都能运行的最低兼容版本。动态渲染并不会替代附件布局转换或同步管理。[Khronos 动态渲染文档](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdBeginRendering.html)
- 需要 swapchain maintenance 扩展以严格管理呈现资源寿命，不能只检查 Vulkan 核心版本。
- 一帧在途，并逐帧等待呈现 fence，便于理解生命周期；它牺牲 CPU/GPU 并行度。扩展到多帧在途时，需要重新组织命令缓冲、深度附件、每帧数据和同步对象，不能只删掉等待。
- 只有一个深度图像，因为当前没有多帧并行使用它。窗口尺寸变化会重建深度图像和图形管线，这对小示例简单可靠，但不是高性能引擎设计。
- 顶点缓冲使用 CPU 可见且 coherent 的内存，直接上传 36 个顶点；数据量极小。大型静态模型更适合 staging buffer 加设备本地内存。本例未使用索引缓冲；按面区分颜色时，即使用索引也通常需要 24 个面顶点，不能简单把 8 个角点共享为 8 种面颜色。
- 目前没有纹理、光照、MSAA、模型导入、鼠标相机、着色器热重载或设备丢失恢复。着色器修改需要重新构建并重启程序。

## 下一步可做的小实验

1. 暂停旋转，改变模型矩阵乘法顺序，预测再观察立方体的姿态变化。
2. 临时关闭深度测试，观察各面绘制顺序如何影响错误遮挡，再恢复。
3. 修改近/远裁剪面与相机距离，观察裁剪；近裁剪面不能设为 0。
4. 新建独立的 `02_indexed_cube`，加入索引缓冲，并比较顶点数量。
5. 再用独立示例加入纹理与描述符，避免一次把整个渲染器抽象得过重。

后续讨论会直接指出实际术语或方案问题，同时区分“为了学习而做的简化”和“会导致错误的实现”。

## 2026-09-08：从示例进入编辑器

现在已经出现明确的共用需求：运动学 demo 与正式编辑器都使用 Win32 / Vulkan / ImGui 和 LaTeX 资源，因此这些实现已分离到 `src/platform`、`src/math` 与 `assets/formulas`。上文关于深度附件和立方体绘制的说明仍只适用于立方体示例。

正式编辑器以“图元”和“编辑命令”为基本抽象。图元描述画什么，运动属性描述如何随时间变化，编辑命令描述如何修改场景。MCP 服务端调用同一套命令，避免鼠标和程序控制各自维护不同状态。注册表、版本迁移和具体扩展步骤见 [编辑器架构](editor-architecture.md)。

Vulkan 能完成这个项目，但图形 API 不提供物理求解、数学排版或编辑器状态管理。这些需要各自建模：当前运动使用解析式，公式使用 MiKTeX 生成的缓存，场景和历史由 C++ 文档层管理。后续自动推导应增加物理量/方程模型，而不是把绘图代码直接扩展成求解器。
