# 图元、编辑命令与 MCP 边界

“编辑器”是准确的产品称呼；“tool”通常指单个可调用工具。“原图形”建议称为**图元**，“原操作”建议称为**编辑命令**。MCP 是通信协议，实现物是 **MCP server / MCP 服务端**。LaTeX 负责数学排版，MiKTeX 是提供排版引擎和宏包的发行版；Vulkan 负责把图形画到屏幕，并不理解公式或求解物理题。

这次已有 demo 和编辑器共用窗口、字体、公式资源的实际需要，因此抽出共用层；没有把立方体强行塞进同一个渲染框架。

```text
鼠标 / 属性面板 ──┐
                  ├─ Editor.dispatch ─ Workspace ─ Document(scope) ─ JSON / 独立历史
MCP SDK ─ 本地管道 ┘                       │
                                  evaluate(time)
                                          │
                                 图元绘制注册表
                                          │
                                ImGui / Vulkan host
```

## 模块

| 位置 | 责任 |
| --- | --- |
| `src/editor/workspace.*` | 显式 scope 路由、主场景与组件草稿生命周期、发布事务、分别保存状态 |
| `src/editor/component.*` | 参数范围、单向绑定表达式求值、静态子图元实例化与整体变换 |
| `src/editor/document.*` | 图元与命令注册、场景校验、原子提交、历史、JSON 持久化、运动状态求值 |
| `apps/editor/editor.*` | 画布、选取/拖动、属性编辑、时间轴、图元绘制、公式资源校验 |
| `src/editor/pipe.*` | 有界、非阻塞、仅本地的 UTF-8 JSON 请求/响应；UI 线程执行命令 |
| `src/platform/vulkan_host.*` | Win32 窗口、Vulkan 生命周期、ImGui 后端、字体图集、窗口测试钩子 |
| `src/math`、`assets/formulas` | 公式显示与离线 LaTeX 资源生成 |
| `mcp/server.py`、`bridge.py` | 官方 MCP SDK 与工具声明、本地管道传输、工作区文件范围 |
| `examples` | 保留独立学习示例；运动学 demo 复用窗口层 |

场景版本是 `version: 1`。图元以稳定字符串 `type` 和 `id` 保存，不保存 C++ 枚举下标、对象指针或 Vulkan 句柄。绘制顺序就是对象数组顺序。未知扩展字段会保留；未知图元类型和文档版本会明确拒绝，避免打开后静默丢图。

## 扩展图元

1. 在 `Registry` 注册稳定类型名、中文名称、默认属性与校验函数。
2. 在 `Editor::initializeRenderers` 注册绘制回调；需要复杂选取形状时补充命中测试。
3. 常规数值属性可扩展属性面板；复杂属性先使用已有 JSON 面板。
4. 新类型会出现在图元目录和左侧工具栏，MCP 的通用创建命令无需新增协议方法。

图元注册不等于运行时加载任意 DLL。v0.1 的扩展是在源码中注册并重新编译；以后若明确需要第三方插件，再增加 ABI/版本/资源所有权约定。删除或改变已有类型时，应提供 JSON 迁移或明确不兼容版本，而不是复用旧类型名改变含义。

## 扩展编辑命令

`Document::registerCommand(name, description, handler)` 注册命令。处理器只修改传入的候选场景，不应写文件、发消息或创建 GPU 资源。整批处理完成后才运行校验并提交。这样即使后续命令失败，先前的候选修改也不会泄漏到真实场景。

新增命令共用批处理、修订检查、撤销、重做和 MCP `apply_commands`。修改命令语义需要保持旧调用兼容，或引入新名字/版本。读操作与保存文件不是可撤销的场景命令，应留在服务边界。

每个文档的撤销历史最多保留 100 步，历史回溯另保留最近 101 个文档状态；都使用场景快照，单场景限制 900 KB、1000 个对象。这是有界、容易验证的初版实现；数据规模变大后，再改成反向命令或结构共享。拖动只在松开鼠标时提交；拖动中若 MCP 改变修订，预览会取消，避免把旧拖动位置写入新场景。

统一操作日志由 `Document::dispatch(request, source)` 记录：界面明确使用 human，管道边界明确使用 mcp，不接受请求 JSON 来覆盖来源。撤销快照附带原事务 event ID；撤销/重做日志关联这个 ID。日志不因撤销或新分支而删除，失败请求也保留，而查询和动画推进不创建历史事件。来源是输入路径，不是身份认证。

日志是按会话追加的 JSONL，包含初始场景和命令；内存用于分页显示，磁盘保留完整记录。它不是完整事件溯源/自动恢复系统，不承诺跨版本自动回放。落盘失败后停止追加以免在半行后继续制造不完整记录，并通过界面/API 报警，保留后续内存历史。

## 物理与教学表达

匀加速运动附着在任意独立图元上，显示对象和运动规律分离。绑定支持“跟随位置”和“显示速度”，要求目标是独立对象；暂不引入层级与循环依赖。步骤只决定图元可见性，时间只决定物理状态，二者可以独立回退。

公式、题目文字和物理参数尚没有符号语义绑定。改变参数不会自动改写注释，也不会验证公式是否适用。若要进一步实现自动推导，应该新增可校验的物理量/方程模型，由其产生场景和公式；直接把绘图 API 叫作“物理求解器”会混淆职责。

## MCP 与一致性

MCP 与鼠标最终调用同一个 `Editor.dispatch`。管道轮询在 UI 主线程处理，避免绘图和写场景发生数据竞争；窗口最小化时仍定时处理请求。每次管道连接只执行一个请求，大小不超过 1 MB，闲置连接 10 秒回收。桥接端不会自动重试已发送的修改。

MCP 编辑默认触发窗口显示/恢复请求，窗口层在下一次绘制前消费请求。画布记录自身实际绘制的 revision/time，在成功提交呈现后更新可查询状态；不能直接拿文档最新修订冒充已渲染修订，因为属性面板可能在本帧画布之后才修改文档。

`expected_revision` 是并发控制，不是权限控制。MCP 保存路径另行限制在工作区；管道使用 Windows 所有者 ACL 并拒绝远程客户端。没有联网服务端口，也不让模型上传或执行 C++/TeX 代码。真正的 MCP 生命周期与消息由 [官方 Python SDK](https://github.com/modelcontextprotocol/python-sdk/tree/v1.x) 实现。


## v0.2：文档作用域、参数化组件和回溯

见 [设计决策 ADR-0001](decisions/0001-components-and-history.md) 与 [使用和格式说明](components-and-history.md)。`Workspace` 保有一个主场景和一个可选组件草稿。所有修改先明确 scope，再交给同一个 Document 实现；两份 Document 之间不共享撤销、播放游标或日志。GUI 标签页只是选择视图，不决定未带 scope 的 MCP 请求目标。

组件定义作为完整快照嵌入主场景，实例引用定义 ID 并保存参数覆盖值和变换。发布通过 `install_component` 原子事务更新快照，验证所有已有实例；不把草稿内部每一步复制进主场景。历史状态因此具有独立、稳定的定义数据，不会因工作区中的草稿变化而悄悄改变过去的画面。参数是有界数值，表达式不运行代码，不形成属性依赖图；本版不支持组件嵌套。

历史回溯使用独立于 head 的可选 revision 游标。`scene()` 给画布返回预览文档，`snapshot().document` 给修改者返回权威 head；`displayRevision` 明确二者的差异。预览禁止文档修改，`restore_preview` 将旧快照作为新事务提交。窗口呈现状态同时记录 scope 和 displayRevision，防止把草稿的 r1 和主场景的 r1 混为一谈。

快照上限是数量和单文档大小限制，不是整个进程内存的硬配额。大场景反复编辑时 JSON DOM 的实际内存可能显著高于序列化大小；后续有大规模文档需求时再引入结构共享及总内存预算，不能宣称当前适合大型 CAD 场景。
